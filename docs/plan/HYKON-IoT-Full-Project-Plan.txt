2. PRODUCT REQUIREMENTS (PRD-1)
=====================================================================

Goal:
  Three kinds of users log in to one website. Each passes its own
  access step and then sees one dashboard with four pages:
  OVERVIEW, SYSTEMS, ACCOUNTS, WARNINGS. What each user can see and
  do depends on the role.

Roles:
  USER               = customer who owns inverter/UPS devices
  DISTRIBUTOR_ADMIN  = admin of one distributor (sells/installs devices)
  HYKON_ADMIN        = HYKON main admin (whole company)

---------------------------------------------------------------------
FLOW 1 - USER (customer)
---------------------------------------------------------------------
  Register (name, email, password)  ->  Login (email + password)
  -> click FEATURES page
  -> DEVICE ACCESS page: enter Device ID + Serial Number
  -> success -> DASHBOARD

  Dashboard for USER:
    Overview  : NOT visible
    Systems   : VISIBLE - only the user's own devices, table format
                (table already exists in the UI)
    Accounts  : NOT visible
    Warnings  : VISIBLE - warnings of the user's own devices only

  Extra:
    - User can ADD a 2nd / 3rd / more device (Device ID + Serial).
    - User CANNOT add distributors.
    - User can see which distributor their device is under, plus the
      install location and device details.
    - After the first device, the access page is skipped on later
      logins (decided).

---------------------------------------------------------------------
FLOW 2 - HYKON ADMIN (main admin)
---------------------------------------------------------------------
  Login with the HYKON admin email/password (only HYKON has this;
  users and distributors can never get it)
  -> click FEATURES page
  -> NO device access page
  -> DASHBOARD directly

  Dashboard for HYKON ADMIN:
    Overview  : everything - all products/systems sold or shipped
                from the company, which user is under which
                distributor
    Systems   : all devices
    Accounts  : all users, distributors, branches
    Warnings  : all warnings

  Extra:
    - Can add distributors, branches, distributor admins.
    - Can add devices for users. Can add everything.

---------------------------------------------------------------------
FLOW 3 - DISTRIBUTOR ADMIN
---------------------------------------------------------------------
  Login with the distributor admin email/password (only for them)
  -> click FEATURES page
  -> DISTRIBUTOR ACCESS page: enter Distributor ID + Branch
  -> success -> DASHBOARD

  Dashboard for DISTRIBUTOR ADMIN:
    Overview  : only counts for devices/customers under this
                distributor (uses the existing UI cards/texts)
    Systems   : all devices under this distributor
    Accounts  : visible in menu, but clicking shows
                "Not accessible for distributors"
    Warnings  : warnings of customers/devices under this distributor

  Extra:
    - Can add customers and devices for users (inside own
      distributor only).

3. PERMISSION MATRIX
=====================================================================

Pages               USER          DISTRIBUTOR_ADMIN       HYKON_ADMIN
-----------------   -----------   ---------------------   -----------
Overview            hidden        own distributor counts  everything
Systems             own devices   own distributor devices all devices
Accounts            hidden        "Not accessible" (403)  everything
Warnings            own devices   own distributor         all

Actions                       USER        DISTRIBUTOR_ADMIN  HYKON_ADMIN
---------------------------   ---------   -----------------  -----------
Self-register                 yes         no                 no
Login email + password        yes         yes                yes
Access gate                   Device ID   Distributor ID     skipped
                              + Serial    + Branch
Add own extra device          yes         -                  -
See distributor + location    yes (own)   yes                yes
Register device to customer   no          own distributor    any
Create customer accounts      no          own distributor    yes
Create distributors/branches  no          no                 yes
Create distributor admins     no          no                 yes
Acknowledge warnings          own         own distributor    all

Account creation rules:
  - POST /api/v1/auth/register ALWAYS creates a USER.
  - The first HYKON_ADMIN is seeded from environment variables
    (never from a public form).
  - DISTRIBUTOR_ADMIN accounts are created only by HYKON_ADMIN and
    belong to exactly one distributor.
  - Security lives in the backend. Hiding a menu item is NOT
    security; every API checks role + data scope.

10. DATA MODEL
=====================================================================

roles          id, name  (USER, DISTRIBUTOR_ADMIN, HYKON_ADMIN)
users          id, name, email (unique), password (BCrypt), status,
               role_id, distributor_id (only for distributor
               admins), phone, created_at, updated_at
refresh_tokens id, token, user_id, expires_at, revoked, created_at
distributors   id, code (unique = "Distributor ID"), name,
               contact_email, phone, status, created_at
branches       id, distributor_id, code, name, city, address,
               status   (unique: distributor_id + code)
devices        id, device_uid (unique = "Device ID"),
               serial_number (unique), product_type (INVERTER/UPS),
               model, capacity_va, distributor_id, branch_id,
               owner_user_id (null until claimed), install_address,
               city, latitude, longitude, status, installed_at,
               last_seen_at, created_by
access_verifications  id, user_id, kind (DEVICE/DISTRIBUTOR),
               device_id or branch_id, verified_at
readings       id, device_id, recorded_at, ac_input_v, ac_output_v,
               load_w, battery_v, battery_pct, frequency_hz,
               temperature_c, charging_state   (fields confirmed in
               Phase H)
alerts         id, device_id, type, severity (INFO/WARNING/
               CRITICAL), message, status (ACTIVE/ACKNOWLEDGED/
               RESOLVED), raised_at, acknowledged_by, resolved_at
audit_log      id, actor_user_id, action, target_type, target_id, at

Chain that controls every page:
  Distributor -> Branch -> Device -> Owner (USER)

Scope rule (one service, every query):
  HYKON_ADMIN        -> no filter
  DISTRIBUTOR_ADMIN  -> devices.distributor_id = my distributor
  USER               -> devices.owner_user_id = my id
  Current user always comes from the JWT, never from the request.
  Out-of-scope device -> 404 (not 403), so IDs cannot be guessed.

11. API CONTRACT
=====================================================================

Existing (done):
  POST /api/v1/auth/register    public
  POST /api/v1/auth/login       public
  POST /api/v1/auth/refresh     public
  POST /api/v1/auth/logout      public (refresh token in body)

New:
  GET   /api/v1/me                         all logged in
  POST  /api/v1/access/device              USER
  POST  /api/v1/access/distributor         DISTRIBUTOR_ADMIN
  GET   /api/v1/dashboard/overview         DISTRIBUTOR_ADMIN, HYKON
  GET   /api/v1/systems                    all (scoped)
  GET   /api/v1/systems/{id}               all (scoped)
  POST  /api/v1/systems                    DISTRIBUTOR_ADMIN, HYKON
  PUT   /api/v1/systems/{id}               DISTRIBUTOR_ADMIN, HYKON
  POST  /api/v1/me/devices                 USER
  GET   /api/v1/warnings                   all (scoped)
  PATCH /api/v1/warnings/{id}/acknowledge  all (scoped)
  GET   /api/v1/accounts/users             HYKON
  POST  /api/v1/accounts/customers         DISTRIBUTOR_ADMIN, HYKON
  GET   /api/v1/distributors               HYKON
  POST  /api/v1/distributors               HYKON
  POST  /api/v1/distributors/{id}/branches HYKON
  POST  /api/v1/distributors/{id}/admins   HYKON
  GET   /api/v1/profile, PUT /api/v1/profile,
  PUT   /api/v1/profile/password           all logged in
  POST  /api/v1/ingest/readings            ESP32 (device secret)

All responses use ApiResponse<T>. Lists take page, size, search,
status. Note: the frontend currently calls /api/v1/accounts and
/api/v1/accounts/groups - align names in Phase G (E1 check first).
